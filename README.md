## Задание 1. Автоматизация генерации признаков

**Подход.** Признак истории описывается как типизированная программа в маленьком DSL —
`AGG(сигнал WHERE фильтр трафика GROUP BY ключ OVER окно)`. Программа компилируется в быстрый numpy/numba-код
и в эталонный SQL (DuckDB); семантика «только события строго до момента показа» зашита в компилятор и проверена
тестами, поэтому любой генератор признаков — поиск или LLM — не может сделать утечку. Поверх DSL — автоматический
поиск со скринингом «польза признака поверх текущей модели» и LLM-агент, предлагающий спецификации DSL.

**Главное** (test, LightGBM, среднее по 3 сидам):

| набор признаков | test logloss | test AUC | GAUC random |
|---|---|---|---|
| ручной набор (40 признаков) | 0.4289 | 0.7834 | 0.6378 |
| ручной набор + тюнинг LightGBM | 0.4292 | 0.7831 | 0.6376 |
| автоматический поиск, цель logloss | 0.4245 | 0.7845 | 0.6397 |
| автоматический поиск, цель listwise | 0.4675 | 0.7190 | **0.6575** |
| LLM-агент (2 запуска) | 0.4219 / 0.4217 | 0.7887 / 0.7898 | 0.6479 / 0.6468 |
| **LLM-агент + поиск** | **0.4198** | **0.7908** | 0.6477 |

* Подбор гиперпараметров бустинга (12 конфигураций) не даёт ничего, а признаки, найденные под logloss (поиском и
  LLM-агентом), значимо улучшают logloss относительно ручного набора (парный бутстрап) и ранжирование на
  random-показах.
* Цель поиска важнее точности окон: признаки под logloss почти не улучшают ранжирование внутри пользователя, а
  поиск под listwise-цель находит другие, item-side признаки и даёт лучшее ранжирование random-показов среди наборов признаков
  истории — ценой калибровки.
* «7 дней или 10?»: для отдельного признака окно важно (оптимум на этих данных — 11–30 дней), но поиск по сетке
  {1ч, 1д, 7д, ∞} даёт итоговую модель того же качества (в нашей постановке — без затуханий и с 6 раундами
  вместо 10), что и поиск по непрерывным окнам.
* LLM-агент — самый эффективный генератор кандидатов (75–78% полезных предложений в первом раунде против 28% у
  случайных программ); лучшая точечная оценка — у связки «агент задаёт стартовый набор, поиск дорабатывает» (один запуск).

## Задание 2. RL-дообучение GPT-2 рекомендера

**Подход.** GPT-2 (2 слоя, d=64) на ID треков + маленький repeat-head как исходная политика π_ref; reward model —
каузальный трансформер по парам (трек, отклик), две независимые RM на непересекающихся половинах пользователей
(A — награда, B — судья); RL — REINFORCE с leave-one-out бейзлайном и точным KL по всему каталогу, 5 функций
награды, одношаговый и 5-шаговый режимы, 24 прогона с повторами по сидам. Для одного шага посчитан точный оптимум
π_β ∝ π_ref·exp(r/β) — эталон для сравнения с RL.

**Главное:**
* Мягкое RL (β=0.1) не меняет релевантность значимо, но и награду повышает мало (+0.004 по RM-A).
* Дальше — reward hacking, вид которого задаёт награда: доля дослушивания → короткие треки и концентрация выдачи,
  секунды прослушивания → коллапс «всем один трек», лайки — в основном переоптимизация под шум RM.
* RL при равном KL (одношаговые прогоны) получает 31–75% прироста точного оптимума по оптимизируемой RM, но, как правило, теряет меньше релевантности (15 из 18 прогонов);
  KL выходит на плато и не растёт при длинном обучении (один 6000-шаговый прогон).
* В 5-шаговой генерации контекст быстро дрейфует, greedy зацикливается, а награда по симулятору систематически
  завышена — её нельзя сравнивать с реальной.
* «Долгосрочный» прокси (продолжение сессии) слабый и смещён длиной трека; единичное значимое улучшение не
  воспроизвелось на других сидах.
